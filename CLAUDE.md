# CLAUDE.md — open-vedic-calc

This repo is a generic, standalone Vedic (BPHS) astronomical calculation service, licensed AGPL-3.0-only. It is reached only over HTTP by a bearer-token-holding caller. Rules below supplement the workspace CLAUDE.md; they do not replace it. That parent file is inherited here automatically, but **the skills it names are not** — only `CLAUDE.md` traverses upward. When a skill the parent names is absent from your session's skill list, the parent states where to Read it; an unresolved skill is a file to open, never a rule to skip.

## Product neutrality — absolute

This is a public AGPL repo. It must **never** name, hint at, or link the proprietary consumer that calls it — not in code, comments, docstrings, tests, commit messages, PR titles/bodies, issues, or docs. Refer to callers only in generic, role-based terms: "the caller", "the HTTP client", "the consumer". "The downstream backend" is acceptable only as a role description, never paired with a name.

The CI gate `ci/check_no_proprietary_refs.py` (run by `.github/workflows/ci.yml` on every change, including docs) is the enforcement mechanism. `_FORBIDDEN` is a **list** of compiled patterns: a legacy base pattern (the standalone word this file's own guard describes, excluding the Swiss Ephemeris URL and the astronomy/astronomical domain words) plus zero or more additional brand tokens read at runtime from the `PROPRIETARY_REF_TOKENS` env var (comma-separated), which CI populates from a GitHub Actions secret of the same name (`.github/workflows/ci.yml`, `boundary` job `env:` block). Standing rule: keep the secret's token list current as the consumer's branding evolves — a token set that only guards a superseded name silently permits a leak; updating it when you learn the brand or infra identifiers have changed is required work, not optional (an **owner** action: only the repo secret's value changes, never this file).

Critical subtlety: do **not** write the literal brand token into this CLAUDE.md, into the gate file's plaintext, into its tests, or into any other tracked file — the file is public, and the token itself would leak the association. The forbidden-term list beyond the legacy base pattern must be maintained out-of-band, exclusively via the `PROPRIETARY_REF_TOKENS` secret injected at CI time — never as public plaintext. If asked to "add the brand to the gate," the correct implementation is adding/rotating that secret's value, not editing source. When the env var is unset (e.g. a fork or external PR without secret access), the gate falls back to legacy-only matching and does not fail — absent optional config is not itself a leak.

**The gate scans the full range of commits under review, and it DERIVES that range rather than being handed one — because the handed-one version scanned a single message on exactly the shapes that mattered.** `ci.yml` used to interpolate `${{ github.event.before }}..${{ github.sha }}` into the step's `run:` body. Measured on five real runs of this repository's own boundary job (`gh run view <id> --log`), that produced `0000…0..<sha>` on a branch's **first** push, `<before>..<sha>` on a later push, `..<sha>` on a pull_request `opened`/`reopened`/`edited`, and `<prev head>..<merge sha>` on a `synchronize`. Two of those four scan **one** message. The null sentinel is correctly refused as unresolvable, so a first push falls back to HEAD alone — and a first push is precisely the one carrying every commit on the branch (measured here: **six** commits on `claude/guard-batch2`'s first push, **four** on another, one message read each). Worse, `github.event.before` exists only on `synchronize`, so on the other pull_request actions the expression rendered empty and the range became `..<sha>` — git for `HEAD..<sha>`, and `actions/checkout` has put HEAD *at* `github.sha` (the run log reads `HEAD is now at bf8cc63 Merge 3ccd529… into dd2a533…`). The range was therefore empty, the fallback read HEAD, and HEAD was GitHub's synthetic **merge** commit, whose message carries no author-written text at all: **zero** real messages scanned, not one.

`resolve_commit_range` now decides in Python, from `GITHUB_EVENT_NAME`, `GITHUB_SHA` and the event payload at `GITHUB_EVENT_PATH` — the same "GitHub forwards facts, the policy decision is made where it is testable" shape `ci/check_pr_text.py` uses, and it means **no `${{ }}` expression is interpolated into that `run:` body at all**. On a pull request the range is the payload's own `base.sha..head.sha` (`github.sha` is the merge commit and is deliberately excluded); on a push a real `before` wins and the null sentinel falls back to `origin/<default_branch>..<sha>`. Every object name from the payload is validated as hex before it is spliced into a range — `git log` reads `--flags` positionally, so an unvalidated field is argument injection, not merely a wrong answer. Three things are deliberate: a derivation that fails **under GitHub Actions** on a push or pull_request is a **refusal** (every fact it needs is one GitHub always supplies, so failing means something is wrong), while the same failure locally is not (a developer has no event payload and never did); `base..head` **over**-scans when a branch has merged its base into itself, which is the fail-safe direction; and the **number of commit messages actually read is printed on every run**, because a range naming six commits and a scan that read one are indistinguishable at exit 0 — which is exactly how this survived. Contract: `ci/tests/test_check_no_proprietary_refs.py::TestTheCommitRangeIsDerivedFromTheEvent` (both trigger shapes, plus the old shapes re-measured so the fix is judged against a demonstrated defect) and `::TestTheWorkflowWiresTheDerivation` (a fix nothing invokes is not a fix — it reds if a range argument or a `${{ }}` expression returns, or if `fetch-depth: 0` goes away).

**The commit-message read is UTF-8 at BOTH ends of the pipe, and an unreadable message is a REFUSAL, never a pass.** `git log` is invoked with `-c i18n.logOutputEncoding=UTF-8`, so git transcodes each message into that encoding whatever the contributor's own git config says (measured: `i18n.logOutputEncoding=ISO-8859-1` in repository config makes `git log` emit latin-1 bytes, and a `-c` override beats it); the raw bytes are then decoded *here*, strictly, rather than inside `subprocess`. `text=True` decodes with the **locale** codepage — cp1252 on a Windows checkout — and does it on a reader thread, where a `UnicodeDecodeError` kills the thread and hands back `stdout=None`. Measured on the commit before the fix, that broke the two branches *differently and both wrongly*: the **range** branch (what CI passes) died with `AttributeError: 'NoneType' object has no attribute 'strip'` — a crash, not a verdict — while the **fallback** branch, which is exactly what the locally mandated `python ci/check_no_proprietary_refs.py` uses, turned that same `None` into an empty list, so the gate scanned **zero** commit messages and printed `OK: no proprietary consumer references found.` with a forbidden token sitting in the message it had just failed to read. A silently disarmed boundary gate is strictly worse than a crashing one. Strict-and-refuse rather than `errors="replace"` is a decision about *this* gate specifically, because it SCANS for tokens: replacement cannot hide an ASCII token (UTF-8 is self-synchronising, so ASCII bytes always decode to themselves, and U+FFFD is not a word character, so the legacy word-boundary pattern still matches beside one) but it does destroy a token spelled with a non-ASCII character — measured, such a token encoded as latin-1 decodes to a replacement character mid-word and stops matching — so an unreadable message is treated as possible concealment, not as absence. `CommitMessageDecodeError` is deliberately **not** an `OSError` subclass: `main` absorbs `OSError` so an absent git degrades quietly, and absorbing the refusal would restore precisely the silent pass it replaces. The sibling helper in `tests/test_line_endings.py` pins its encoding the same way but takes `errors="replace"`, and that asymmetry is deliberate and recorded in its docstring — it reaches its verdict from fields that are ASCII by git's construction, so no replacement character can change what it decides.

**The three arms that enforce that pipe are alias-aware, because ONE REBINDING used to defeat all three at once.** The arms find the gate's git calls by parsing it, and the matcher accepted exactly one spelling — an attribute named `run` on a `Name` whose id is literally `subprocess`. Measured: planting `sp = subprocess` and an unpinned `sp.run(["git","log","--format=%B","-1"], …)` — a second commit-message read bypassing `_run_git_log`, which is precisely what Arm B exists to refuse — left **all four** arms GREEN. The collector now resolves the ordinary binding constructs (`import … as`, `from … import [as]`, `from … import *`, `sp = subprocess` transitively, and `r = subprocess.run`, which the tree-wide sibling in `ci/tests/test_subprocess_decoding.py` recorded as an open bound of its own until it was closed there too — it is now resolved in both, and what still separates them is the refusal half below, which a tree-wide guard cannot have because `obj.run(…)` is ordinary code out there) **and, more importantly, refuses what it cannot resolve**: any `.run(…)` whose receiver is not a name proved to hold the module, plus any `getattr(<module>, …)`, is recorded UNRESOLVED and reds the build. That refusal half is what makes the attribute form complete without a finished enumeration — the guard need not know how a name came to hold the module, only that it cannot prove it does not. The bare-name form does still rest on enumeration, so the claim is *measured* rather than asserted: the visitor's module-scope binding set is compared against `symtable`, the compiler's own tables, and asserted **identical in both directions** — a construct the visitor does not model reds on the commit that introduces it. This sentence used to cite the size of that set as "28 names"; the number is deliberately gone, because nothing recounted it and it was already **37** by the time anyone looked. The equality is the claim; the cardinality was decoration that rots (this file's own rule, one paragraph on). The `getattr` hole was found by the guard's own probe list, not by reasoning — which is the argument for writing evasions down as test data rather than as prose. Contract: `ci/tests/test_check_no_proprietary_refs.py::TestTheRunCallCollectorSeesEveryBinding` and `::TestTheGateItselfHasNoUnresolvableRunCall`.

**The FILE scan is strict too, and for the same reason.** It used to read each file with `read_text(encoding="utf-8", errors="replace")`. That encoding was already pinned, so the file half was never locale-dependent — but *lossy is not the same as safe*, and the masking argument that decided the commit-message policy applies here unchanged: replacement cannot hide an ASCII token, but it destroys a token spelled with a non-ASCII character, which is exactly what a token arriving from a secret this repo cannot read may be. Both scanned inputs now decode through the one `_decode` helper, so the policy cannot be applied to one and forgotten on the other, and an undecodable file joins the same `refusals` list a bad commit message does — rc 1, naming the file, never `OK:`. Three properties are deliberate: the decode sits **outside** the `except OSError` arm (an unreadable file is skipped, an *undecodable* one is refused — absorbing the second into the first would restore the silent pass); a refusal **collects and continues** rather than raising, or one undecodable file would become a way to hide a leak in a readable one later in the walk; and `FileDecodeError`, like `CommitMessageDecodeError`, is **not** an `OSError` subclass. Measured before the switch: of the **104** files in the scan set, **0** failed a strict UTF-8 decode, so strictness costs nothing on a healthy tree and a failure is signal rather than routine noise. Contract: `ci/tests/test_check_no_proprietary_refs.py::TestFileScanDecoding`, which measures the masking itself before asserting it is shut — the premise is verified, not assumed.

**And the FILE scan's SCOPE comes from git, not from a directory walk.** It is `git ls-files -z --cached --others --exclude-standard` — everything that ships, plus everything one `git add` away from shipping (the gate's whole purpose is to run before the push that would publish the leak, and at that moment the offending file is usually still untracked), minus everything git is told to ignore. The walk it replaces was wrong in **both** directions at once. Fail **open**: `_SKIP_DIRS` drops a directory by NAME, so a tracked file under any of those names shipped unscanned — nothing tracked sits under one today, which is exactly why the hole was invisible, and measured, a tracked `data/notes.md` carrying a synthetic token was answered `OK: no proprietary consumer references found.` Scope **inflation**: measured 2026-08-26 in the shared root checkout, the walk enumerated **221** scannable files against a real set of **106** — **115** extra, **111** of them another branch's working tree under `.claude/worktrees/` — so the local gate's verdict depended on which unrelated branches happened to exist beside it. `-z` is not optional (git otherwise QUOTES a non-ASCII path and octal-escapes its bytes — the measured fail-open `ci/check_pytest_collection.py` shipped), and the listing is read as **bytes** and decoded in-process, so a filename that is not valid UTF-8 answers "git cannot answer" rather than dying on a reader thread. A walk is kept **only** as the fallback for a tree git cannot describe, and it announces itself; the new failure mode the switch introduces is closed in the same change — a scan that examined **zero** files is a REFUSAL, never a clean verdict, because `git ls-files` can answer rc 0 with no output where a walk of a populated tree cannot. Contract: `ci/tests/test_check_no_proprietary_refs.py::TestFileScanScopeComesFromGit`.

**And having got the right SET, the gate then opens ALL of it — there is no extension allowlist.** Asking git the right question fixed the scope; it did not fix what the gate did with the answer. `_is_scannable` admitted twelve extensions (`.py .md .yml .yaml .toml .txt .sh .ps1 .cfg .ini .json .dockerfile`) plus the exact basename `Dockerfile`, so a file whose extension nobody had thought of was enumerated, **skipped, and counted towards a clean verdict** — the gate printing `OK:` about a file it never opened, which is the directory blacklist's fail-open shape one layer along. Measured 2026-08-26, that left **EIGHT** tracked files outside the scan: `Dockerfile.test` (its `.test` suffix is not in the set and its basename is not exactly `Dockerfile`, so it matched neither arm — the gate read `Dockerfile` and skipped the file beside it), `.env.example`, `.github/CODEOWNERS`, `.gitattributes`, `.gitignore`, `.python-version`, `LICENSE` and `uv.lock`. The first three are prose a human writes about the deployment and about who owns which path — the register a downstream consumer gets named in. **Lock files are IN, deliberately**: `uv.lock` is tracked and a raw file view publishes it exactly like the code, it records dependency **names** and index URLs, and being machine-generated is the argument *for* scanning it rather than against — a private package name or index host lands there without a human ever typing it into a file the gate reads. **Binary is a REFUSAL, never a skip.** Widening means an unreadable file now reaches the strict decode, and the existing answer stands: it joins `refusals`, is named on stderr, and exits non-zero — "I could not read it" may never be recorded as "there was nothing in it", which would otherwise hand anyone a way to park a leak behind an unrecognised extension. Measured over the whole scan set at the time of the change: **0** files carry a NUL in their first 8 KiB and **0** fail a strict UTF-8 decode, so strictness costs nothing on a healthy tree; the local gate went from 106 to 114 files scanned. Contract: `ci/tests/test_check_no_proprietary_refs.py::TestEveryEnumeratedFileIsScanned`, whose last test asserts **enumerated == scanned** on the real tree, so reintroducing any filter — an extension set, a name test, a size cap — reds on the commit that adds it.

**A PR's TITLE and BODY are scanned too, by a separate checker — they are neither tracked files nor commit messages, so the tree gate never saw them.** They live only in GitHub's database, they can be edited after the PR is opened, and a PR page is world-readable and indexed exactly like the code. That made PR text the one artifact written most freely — by hand, while thinking hardest about the downstream consumer — with nothing checking it. `ci/check_pr_text.py` closes it, wired as the `pr-text` job in `ci.yml`. Four things about it are deliberate. (1) It **imports the pattern machinery from the tree gate** rather than reimplementing it, so the two can never disagree about what a forbidden token is. (2) The PR text reaches the process through `env:`, **never interpolated into a `run:` body** — a `${{ }}` expression is textual substitution performed *before* the shell parses the command, and anyone may open a pull request against a public repo, so a title carrying shell metacharacters would execute; `ci/tests/test_pr_text_check.py::test_pr_text_is_never_interpolated_into_a_run_body` pins that across *every* workflow, not just this one. **Both routes, not just the direct one:** `env:` is safe only while the `run:` body reads a SHELL variable (`"$PR_TITLE"`), and writing `${{ env.PR_TITLE }}` in the body throws that away — the same textual substitution, performed before the shell parses the command, on a value that was forwarded correctly. The dangerous env names are **derived** from each workflow's own `env:` blocks (any key whose value carries PR text, so renaming the variable is no escape) unioned with this repository's two conventional names as a floor — measured, derivation alone fails open when the assignment lives at another level and the step's own `env:` records nothing. Measured 2026-08-26: **no** workflow here takes the env route today, so that half is a preventive control, not a fix. **Both routes match on a NORMALISED expression body**, because GitHub accepts index notation and resolves property names case-insensitively: `${{ github['event']['pull_request']['title'] }}` and `${{ GITHUB.EVENT.PULL_REQUEST.TITLE }}` substitute exactly what the dotted spelling does, and measured, all three were unflagged before normalisation — the direct half of that gap predating the env route entirely. **Whitespace is normalised away too, and that was DETERMINED, not assumed.** `${{ env . PR_TITLE }}` and `${{ github ['event'] ['pull_request'] ['title'] }}` were both measured unflagged, and whether they even *evaluate* is a question about GitHub's expression grammar — answered by reading the engine: the runner's `LexicalAnalyzer.TryGetNextToken` (the C# `Expressions2` library that evaluates `${{ }}`) advances past `Char.IsWhiteSpace` **unconditionally** before reading the character that decides a token's type, so whitespace never becomes a token and `env . PR_TITLE` yields the identical token stream to `env.PR_TITLE`. GitHub's own editor reimplementation, `actions/languageservices`, agrees — its lexer has an explicit *ignore whitespace* arm emitting nothing for space/tab/CR/LF, and its `.` arm keys off the **previous token**, not the previous character. So the spaced spelling is legal, and it was an evasion to close rather than a bound to record. Both routes and the env-key *derivation* read the normalised body, so a spaced **assignment** registers its forwarded key too. Two bounds are recorded rather than assumed away: only a *literal* index is resolved, since a computed one (`env[format('PR_{0}','TITLE')]`) would require evaluating GitHub's expression language, which is the modelling this guard deliberately does not do; and the whitespace collapse runs over the whole expression body, string literals included, which can only ever flag **more** — bounded by the don't-over-flag control rather than by parsing the language. The workflow scope itself comes from `git ls-files` and covers **both** `.yml` and `.yaml` — GitHub Actions runs `.yaml` identically, and a `*.yml` glob makes an affirmative "no violations" claim about a file it never opened — with `--others` keeping an untracked workflow in scope (the cheapest moment to catch a violation is the commit that introduces it, and the file is not yet tracked then) and `--exclude-standard` keeping a developer's ignored scratch workflow out. Outside a checkout it fails closed, because "zero workflows found" and "zero violations found" are the same green. **That enumeration is now the repository's ONE definition, `ci/workflow_scope.py`, and it had to be** — this guard got it right while two siblings that ask "does any workflow do X?" were still globbing `.github/workflows/*.yml`: `ci/tests/test_ci_runs_gate_regression_suite.py` and `ci/tests/test_swiss_ephemeris_job.py`. The second is the one that mattered, because every assertion in it has the form *no* workflow narrows the accuracy job, injects `PYTEST_ADDOPTS`, writes `$GITHUB_ENV` or unpins uv — all of which a `.yaml` workflow could have done while the guard reported clean by not looking. `ci/tests/test_environment_convergence.py` already read both suffixes and now delegates too, so those `ci/tests/` guards share one answer rather than one apiece; the fail-closed refusal is a dedicated `WorkflowScopeError` rather than a bare `assert`, which `python -O` strips. **That claim was scoped to `ci/tests/` when it landed, and the two production checkers it honestly excluded are now migrated too, so **every** reader shares the one answer — a claim carried by `ci/tests/test_workflow_scope.py`, not by a number counted here (see the checked-not-counted paragraph below).** `ci/check_workflow_token_scopes.py` and `ci/check_pytest_collection.py` both read **both** suffixes already, so the half-enumeration defect was never present in either and calling them wrong would have been the overclaim; what they lacked was everything only git can supply. ## Engine conventions (astronomical correctness)

- Ayanamsa is LAHIRI. The ephemeris path and sidereal/ayanamsa mode are **THREAD-local** state (pyswisseph >= 2.10's thread-local `swed` struct), **not process-global** — every thread must apply both itself before it calls into `swe.*`/`drik.*`, or it silently computes on the Moshier fallback with the default Fagan/Bradley ayanamsa (~0.88 deg / 53 arcmin off Lahiri) instead of raising. `bphs_core/utils.py`'s `_ensure_thread_ephemeris_state()` applies `swe.set_ephe_path(...)` and `drik.set_ayanamsa_mode('LAHIRI')` once per thread, idempotently; `serialized_ephemeris` calls it on every invocation of every C-library entry point, so a new compute path gets it by construction as long as it carries that decorator — never assume a clean default on a thread that isn't provably decorated. `Chart._compute` additionally re-asserts `drik.set_ayanamsa_mode('LAHIRI')` inline (the first statement of `Chart._compute`, `bphs_core/chart.py`) on top of the decorator's guarantee; keep that re-assertion pattern in any new compute path as defense-in-depth — but the decorator, not the inline re-assertion, is what makes a new thread correct.
- **Ephemeris lock (thread-safety):** the underlying Swiss Ephemeris C library is not documented as safe for concurrent `swe_calc`/`swe_houses` calls from multiple threads — even once each thread's own path/ayanamsa state (above) is correctly configured — and Starlette's request pool + the scan-job pool in `app/jobs.py` both enter it concurrently. Every **new** runtime compute path that calls `swe.*`/`drik.*`/`charts.*` **must** be wrapped in `@utils.serialized_ephemeris` (bphs_core/utils.py) so it (a) gets the per-thread state above applied on every call, and (b) holds the process-wide `EPHEMERIS_LOCK` — and it must be decorated at **inner, millisecond-bounded granularity** (one chart, one day, one instant, one JD conversion), **never around a whole scan**: a whole-scan hold blocks every interactive route and the async submit path for the scan's remaining duration, reversing the "submissions never wait on scan compute" property below. The lock is an RLock, so nested decorated entry points are safe. Add each new entry point to the coverage list in `tests/test_ephemeris_lock.py::test_every_c_library_entry_point_is_serialized` — the test pins only the known set; this rule is the guard for future paths.
- Julian Day discipline (the rule that prevents the tz double-subtraction bug): pyjhora chart/drik functions (`charts.rasi_chart`, `drik.ascendant`, `drik.dhasavarga`, `drik.planets_in_retrograde`) expect a **local-clock JD** and subtract the place timezone themselves internally. Any swisseph call that needs true UT derives it separately as `jd_utc = jd - tz_offset_hours / 24.0` **at the call site** (`Chart._compute`, on the line after its `_jd_from_person` call). Never feed a tz-pre-subtracted JD to pyjhora, and never feed a local JD to a swisseph UT function — the two transports are distinct and are not interchangeable.
- The lagna/ascendant is computed **directly** from swisseph — `swe.houses(jd_utc, lat, lon, b"P")` → `ascmc[0]`, then sidereal-corrected as `(ascmc[0] - ayanamsa) % 360` (the `swe.houses` call in `Chart._compute` and the `sid_asc` assignment that follows it). **Never** take the ascendant from pyjhora's `rasi_chart()[0]`: it double-applies the timezone and lands the lagna tz-hours off. - **Position-flag word: DECLARED in `bphs_core/utils.py` (`POSITION_FLAGS = 65810`) and never inherited.** The third argument to `swe.calc_ut` decides the reference frame every served longitude is expressed in, and it used to come from `drik.PLANET_FLAGS`, which pyjhora builds at *its* import time from five `jhora.const.PLANET_POSITIONS_*` globals. Measured 2026-07-31, this repository unchanged, on two resolves: **pyjhora 4.8.6 → 66386, pyjhora 4.8.7 → 65810**, a difference of **576 = `FLG_NOGDEFL` (512) | `FLG_NONUT` (64)** — 4.8.7 flipped `PLANET_POSITIONS_USE_DEFLECTION` and `PLANET_POSITIONS_USE_NUTATION` from `False` to `True`. **That bump was taken deliberately on 2026-08-21 and the declaration re-derived with it**; the pin is now `pyjhora==4.8.7` and the declared word is `FLG_SWIEPH|FLG_SIDEREAL|FLG_TRUEPOS|FLG_SPEED`. `FLG_TOPOCTR` is deliberately not taken (this service receives no observer altitude), and `FLG_NOGDEFL`/`FLG_NONUT` are no longer taken either — measured, swisseph applies both unasked and reports so in its retflag (requesting 65810 returns **67410**, carrying `FLG_NONUT|FLG_NOGDEFL|FLG_NOABERR` nobody asked for), so the two words are the *same computation*, not merely close: longitude **and** daily speed are **bit-identical** across 72 graha-epoch pairs spanning 1800–2400, 56 answered on Swiss data and 16 on Moshier. Because the pair is now relied on rather than declared, the reliance is **enforced**: `utils._IMPLIED_BY` maps each omitted flag to the declared flag that masks it (`FLG_NOGDEFL`←`FLG_TRUEPOS`, `FLG_NONUT`←`FLG_SIDEREAL` — measured separately; clearing `FLG_TRUEPOS` stops swisseph adding `NOGDEFL` back, while `NONUT` is still added for any sidereal request), and `apply_position_flags` step (0b) hard-fails if a masking flag ever leaves the word while the flag it masks is absent. **The flags are coupled and only one of them currently moves a number.** Measured with the frozen resolve against the real Swiss data files over 1800-01-01..2400-12-31 at one-day steps, 219511 days × 9 grahas: dropping `FLG_TRUEPOS` (geometric → apparent) moves positions by up to **0.016817256° = 60.5421 arcsec** (Mercury, 2353-06-16 00:00 UT; Venus 44.7711″, Mars 38.9693″, Jupiter 30.0595″, Saturn 27.2519″, Sun 20.8489″, Moon 0.7632″, Rahu/Ketu 0.0146″), while dropping `FLG_NOGDEFL`+`FLG_NONUT` moves **0.000000000° on every graha on all 219511 days** — because under `FLG_TRUEPOS` swisseph ignores deflection and aberration outright, and for a sidereal request it applies `FLG_NONUT` unasked (retflag 65602 for a plain `FLG_SWIEPH|FLG_SIDEREAL` request). So the library's word moved and **no golden here could have caught it**: the served numbers were bit-identical, and when the bump was actually taken the tripwire was the *only* thing that went red — measured, `pytest tests/` produced **41 collection errors**, every one the applier's `RuntimeError`, while `pytest ci/tests/` stayed green at 155 passed. That inertness is conditional — clear `FLG_TRUEPOS` and `FLG_NOGDEFL` becomes worth 0.0711″ and `FLG_NOABERR` 20.8557″ (and the 66386/65810 pair, identical under `FLG_TRUEPOS`, separates by up to 0.128869″ without it). Never reason about one of these flags without the others.
- **The position-flag word has three levers, and the serving one is a mutable global built before this package runs.** (1) `jhora.const.PLANET_POSITIONS_*`, read by `jhora.utils.set_flags_for_planet_positions()` on every call — the inherited default, and what moved between 4.8.6 and 4.8.7; (2) `drik.PLANET_FLAGS`, built from (1) at drik's import time and read at call time by `drik.sidereal_longitude`, `drik.dhasavarga` (hence `charts.rasi_chart`) and `drik.planets_in_retrograde` — this is what actually serves; (3) `jhora.const._TROPICAL_MODE`, which makes `drik.sidereal_longitude` ignore `PLANET_FLAGS` entirely and compute with `FLG_SWIEPH + FLG_SPEED` (tropical, ~24° away) — a pinned word that is bypassed is not a pin. `utils.apply_position_flags()` checks the declaration against its own decomposition (0) and against the masking invariant (0b), then **compares (1) against the declaration and hard-fails at import on any disagreement**, then pins (2) and reads it back, then verifies (3). The comparison against (1) is the whole point: pinning alone would silently absorb a dependency that changed its mind, which is the exact failure the 576 move demonstrates — and note that absorbing it is *also* why the declaration had to move to 65810 rather than keep 66386 and pin over the top; an equality you relax to tolerate a disagreement is no longer a tripwire. Scope, stated so it is not discovered later: this is the **planetary position** word only — the ascendant and Bhava-Chalit cusps come from `swe.houses(jd_utc, lat, lon, b"P")` (chart.py), which takes no flag word, and sunrise/sunset use pyjhora's separate `drik.RISE_FLAGS`/`SET_FLAGS` (measured **897 / 898, identical in 4.8.6 and 4.8.7**, so unmoved — and now declared in their own right, see the next bullet). Contract: `tests/test_position_flags.py`; extend it, never weaken it.
- **Sunrise/sunset convention word: DECLARED in `bphs_core/utils.py` (`RISE_FLAGS = 897`, `SET_FLAGS = 898`) and never inherited.** Every panchanga/electional limb is anchored to the day boundary — `drik.sunrise`/`sunset`/`moonrise`/`moonset`, and through them tithi, nakshatra, yoga, karana, the thirty muhurtas and the whole muhurat/lagna-shuddhi scan. Each of those calls `swe.rise_trans(..., rsmi=<word>, flags=PLANET_FLAGS)`, where the **`rsmi` word is DISTINCT from the ephemeris `flags` word `POSITION_FLAGS` pins** and decides *what counts as sunrise*: disc centre vs lower limb, true (geometric) vs apparent (refracted) horizon, rise vs set. The declared convention is swisseph's `BIT_HINDU_RISING` (896) — the Sun's disc **centre** at the **true, unrefracted** horizon (geocentric, no ecliptic-latitude correction), i.e. the classical *madhya-bimba* Hindu sunrise, matching `drik.sunrise`'s docstring and drik's own "geometric, true sunrise/set, refraction not considered" comment. This geometric disc-centre (Surya-Siddhanta) convention is **owner-ruled 2026-08-17**; the civil/almanac upper-limb-at-refracted-horizon convention is a real alternative a secular ephemeris reports, but the choice between them is settled, not an open question. It is load-bearing: **measured at Colombo 2024-03-20, clearing `BIT_NO_REFRACTION` moves sunrise 147.99 s (06:18:01 → 06:15:33)**, so the convention affects every limb measured from the day boundary. **Two levers, not three** — there is no runtime bypass here analogous to `_TROPICAL_MODE`: (1) `jhora.const.RISE_SET_HINDU_RISING`/`_USE_REFRACTION`/`_USE_DISC_CENTER_FOR_RISING`, the three globals `jhora.utils.set_flags_for_rise_set()` reads (the inherited default; flipping each moves the word to 769/770, 385/386, 9089/9090 respectively); (2) `drik.RISE_FLAGS`/`SET_FLAGS`, the mutable serving globals built from (1) at drik's import time. `utils.apply_rise_set_flags()` **compares (1) against the declaration and hard-fails at import on any disagreement** — the dependency-bump tripwire, exactly as `apply_position_flags` does — then pins (2) and reads both back. Pinning is behavior-preserving on the frozen resolve (the library already builds 897/898); the declaration is what makes a future `RISE_SET_*` default-flip legible instead of a silent day-boundary shift no electional golden could see. Contract: `tests/test_rise_set_flags.py`; extend it, never weaken it.
- **Two planet-id spaces exist and they are NOT interchangeable — graha names cross module edges, never raw integer body ids.** pyjhora numbers the grahas by the order of `utils.PLANETS` (Sun 0, Moon 1, **Mars 2, Mercury 3, Jupiter 4, Venus 5**, Saturn 6, Rahu 7, Ketu 8) — the space its chart *outputs* use (`charts.rasi_chart`, `drik.dhasavarga`, `drik.planets_in_retrograde` return these ids). swisseph numbers bodies Sun 0, Moon 1, **Mercury 2, Venus 3, Mars 4, Jupiter 5**, Saturn 6, Uranus 7, Neptune 8, node 10/11 — the space `swe.calc_ut` and `drik.sidereal_longitude` *consume* (pyjhora's own docstring: "The sequence number of 0 to 8 for planets is not followed by swiss ephemeris"). Sun, Moon and Saturn coincide, which is what lets a conflation survive spot checks: pass a PLANETS index to `sidereal_longitude` and a third of the output is right while Mars silently computes **Mercury**, Mercury→Venus, Jupiter→Mars, Venus→Jupiter, Rahu→**Uranus** and Ketu→**Neptune** — wrong celestial bodies, not small errors (measured 2026-07-31: index 7 returned 40.7495° = Uranus where the true node stood at 305.5916°). This shipped twice, in the transit endpoint's planet table and in the electional scorer's lord/malefic ids. The standing rule: per-body positions are requested **by graha name** through `utils.graha_sidereal_longitude(jd_utc, name)` — the single sanctioned boundary, which resolves names against explicit `swe.*` constants (Rahu = the declared `LUNAR_NODE_BODY`, Ketu = Rahu + 180°) — and `drik.sidereal_longitude` / `swe.calc_ut` are called **nowhere outside `bphs_core/utils.py`**. Never rebuild an id table from `enumerate(utils.PLANETS)`. A compute failure inside the lord/malefic scoring limbs **propagates** — it is never swallowed into a neutral-looking score (a swallowed `except: pass` there once reported wrong astrology as fine). Contract: `tests/test_graha_body_ids.py` — per-graha positive assertions against independent computations, plus an AST scan (parses code, cannot be defeated by comments/strings) that fails any new `sidereal_longitude`/`calc_ut` call site outside the boundary. Extend it, never weaken it.
- **Served clock times use ONE minute-rendering convention — TRUNCATE to the minute the instant falls in — via `bphs_core/muhurat.py::float_hours_to_hhmm`, byte-identical to pyjhora's `utils.to_dms(...)[:5]`.** Every HH:MM a muhurat/panchanga day serves — sunrise, sunset, moonrise, moonset, the 30 muhurtas, the auspicious/inauspicious/chogadiya/rahu-kala windows, and the tithi/nakshatra/yoga/karana end-times — must render on the same clock, because a period BOUNDARY is frequently the SAME instant as an event it is derived from: the night-muhurta division opens at exactly `drik.sunset(...)[0]`, and the chogadiya day/night split and one weekday's rahu-kala edge land on sunset too. `float_hours_to_hhmm` used to ROUND to the nearest minute while pyjhora's own `to_dms` (which formats every drik-computed time string this service then slices `[:5]`) TRUNCATES, so an 18:17:58 sunset served as `sunset` "18:17" but opened its night muhurta at "18:18" — register #176. The fix renders the helper on the library-native truncation (round the residual to whole seconds, then truncate the minute — exactly `to_dms`), and routes sunrise/sunset/moonrise/moonset through it on the float `[0]` so the event and the boundary derived from it pass through one formatter and cannot disagree. The BPHS-accurate value is the underlying float and is untouched by the choice; only the minute LABEL is pinned, and it is pinned to the convention already governing the 10 drik-string categories rather than introducing a second one. Convention chosen over nearest-minute rounding deliberately: rounding would (a) diverge from those 10 library-native categories, re-creating the same disagreement at the chogadiya/rahu-kala boundaries that also coincide with sunset, and (b) shift the minute-rendered sunrise the hora-lord limb consumes, drifting a computation this display fix must not touch. Contract: `tests/test_muhurat_deep.py::TestSingleClockConvention` locks `float_hours_to_hhmm ≡ to_dms(...)[:5]` (so the `[:5]` sites this helper does not itself format can never drift from it) and the served field==boundary invariant across a spread including the half-minute-second band where truncate and round diverge. Never reintroduce a second rounding convention for a served time.
- Origin lesson: this codifies a real ascendant-timezone bug found and fixed in this repo; the rule above is self-contained and does not require any external context to apply correctly.

## Determinism

This is an electional/astronomical engine — outputs must be reproducible.

- Astronomical outputs are golden-value tested against synthetic, non-personal reference charts. `tests/test_calc_regressions.py` is the canonical pattern: synthetic charts only, invariant assertions (e.g. Chart longitudes equal a direct UT swisseph computation for any non-zero timezone). **No personal or family birth data ever enters tests, fixtures, plans, or committed reference files** — synthesize charts or assert invariants instead.
- Any change to a calculation module (`bphs_core/*`) that could shift a numeric output requires a golden/regression test that first failed (per the parent workspace's test-first non-negotiable) and pins the expected value. "It runs" is not sufficient evidence for an accuracy engine.
- Fail-closed determinism governs the electional (muhurat / lagna-shuddhi) pipeline: a limb that cannot be computed must never resolve silently to "fine / auspicious". `tests/test_panchanga_fail_closed.py` is the contract; extend it, never weaken it. One-sentence mandate: a missing limb means visibly degraded, never a clean pass.
- **Which failure mode a limb takes is DECLARED, not uniform — project decision 2026-08-17: a limb failure that can change WHICH time is recommended must RAISE (`bphs_core.muhurat.MuhurtaLimbError`, naming the limb); only genuinely supplementary limbs may degrade, and only behind an explicit per-limb flag.** Every limb in `bphs_core/muhurat.py` used to answer failure the same way — a log line plus a default, a dropped window, or a `None` — so a day assembled from a broken frame was indistinguishable on the wire from a day assembled from a good one. The line is drawn from what `bphs_core/lagna_shuddhi.py` actually reads, not from how central a limb sounds: `_candidate_minutes` builds the ENTIRE candidate-minute set from `auspicious_muhurtas` + the favourable `chogadiya` windows, and `_score_instant` hard-excludes on the Rahu/Yamaganda/Gulika windows and, per activity, on Durmuhurtam/Varjyam, the Vishti karana, the eclipse flag and the adhika-maasa flag, scores on the tithi/yoga names, and derives the hora lord from the served `sunrise`. A dropped window or an unverifiable flag in any of those does **not** make the engine cautious — it deletes a veto or a candidate, silently. Limbs with **zero** reads in that pipeline (moonrise/moonset, the four panchanga end-times, the amrita windows, the 30-muhurta display table, the personal-balam strings) are the ones that may degrade; they name themselves in the additive `degraded_limbs` field, from which the summary `degraded` bool is DERIVED so the two cannot disagree. Corollaries: a NAME and its END TIME are classified separately even when one call yields both (`drik.tithi`/`karana`); a veto flag that resolves to `None` and asks its reader to fail closed is the same silent-drop shape as an omitted window, so `panchaka_free`/`is_eclipse_day`/`is_adhik_maasa` are now always answered here (they stay nullable on the wire, and the consumer-side null-vetoes-too gate stays, for payloads from any other producer); `hard_gate_failed` is retained on the wire and always False from this service, because the three limbs that set it now raise. **At the HTTP boundary a raised `MuhurtaLimbError` is surfaced by the synchronous routes as a structured `422`** — `{"detail": {"code": "muhurat_limb_error", "limb": <name>, "target_date": <YYYY-MM-DD>, "message": <str>}}`, via the `@app.exception_handler(MuhurtaLimbError)` in `app/main.py` — never an opaque `500` and never a `200` with an empty/partial muhurat list. `422` (not a 5xx) matches this service's existing "well-formed request the engine cannot fulfil" convention (date-range caps, member counts, invalid activity); the raise site already logs at ERROR with the traceback, so no observability is lost. The handler is registered against the exception class, so it also covers the synchronous lagna-shuddhi routes; it does **not** fire on the async scan-job path, which captures the same failure into the job's `error` field on its background thread (`app/jobs.py`). Contracts: `tests/test_muhurat_limb_failure_modes.py`, which discovers the `drik` entry points by **parsing** the module and fails any limb carrying no recorded classification, and `tests/test_muhurat_limb_error_route.py` for the route-level envelope — extend them, never weaken them.
- **A rise/set limb's failure mode is unreachable through `except` alone — the library returns a SENTINEL, not an exception.** Measured 2026-08-17 against the real Swiss data files: at latitude 78.0 on 2026-06-21 `drik.sunrise`/`sunset` returned `-59069099.0` rather than raising, `float_hours_to_hhmm` reduced it modulo 24, and the day was served as sunrise **"13:00"**, sunset **"13:00"**, `degraded: False`, `hard_gate_failed: False`, with 30 muhurtas, 16 chogadiya windows and three **zero-width** absolute-veto windows — a complete, clean-looking recommendation resting on a day frame that does not exist. Every rise/set float is therefore range-validated (`muhurat._event_hours`) before it is rendered: over 5980 mid-latitude samples (lat −66..66 step 6, 5 longitudes, 13 dates, all four limbs) the value ran min 0.0033 h / max 26.0241 h with **none** outside `[0, 48)` — the bound is one full wrap wide because an event legitimately lands after local midnight — while of 600 polar sunrise/sunset samples (|lat| 67..89, 3 longitudes, 10 dates) the 228 real events sat inside it and all 372 no-rise cases were large negatives in `[-59073516.0, -59064996.0]`. Generalise: when a foreign call reports "no such event" **in band** rather than by raising, an exception handler around it is dead code, and the guard has to read the value.
- **A dependency's wire shape is pinned by a test that drives the REAL callee — a fabricated fixture validates a fiction, and can pin the defect itself as expected.** Measured 2026-08-05: the 30-muhurta limb served an **empty list behind HTTP 200 on every single request**, with `degraded` reporting `False`. `drik.muhurthas()` returns 30 entries shaped `(name, auspicious_flag, (start_hours, end_hours))`; the parser sniffed `isinstance(entry, tuple) and len(entry) >= 2` — which the real 3-tuple satisfies — then read `entry[0]`, the *name*, as a float hour, so `float_hours_to_hhmm` raised `TypeError` on every iteration and a bare `except Exception` wrapped around the whole loop turned it into a log line. The suite could not see it because the test monkeypatched `drik.muhurthas` with `(6.0, 6.8)` 2-tuples the library has never returned, and then **asserted the empty list as the expected result** — encoding the bug as correct behaviour, so a correct implementation would have failed the suite. Five standing rules follow, and they generalise to every `drik.*`/`swe.*` return this engine parses:
  - Every limb that parses a third-party return carries at least one test driving the **unpatched** callee, asserting the **structured** result — how many entries, which names, what boundaries. `assert result != []` passes on a single garbage entry and is not evidence.
  - A broad `except` wraps **only** the foreign call, never the parsing of its result. Use `try/except/else`: the environmental failure mode (sunrise/sunset at extreme latitudes) degrades visibly inside `except`; the parse sits in `else`, where a contract break **raises** instead of being served as silence. An empty field a consumer cannot distinguish from a real answer is worse than a 500 — the 500 is visible and recoverable.
  - Monkeypatching a foreign function is legitimate to simulate **failure**, never to invent a **success** shape. If a test needs a success shape, it must be the shape the library actually produces, pinned by a sibling test that reads the library directly.
  - Parse strictly and reject an unexpected **count** as well as an unexpected shape: positional labelling (`_MUHURTA_NAMES[i]`) silently mislabels every window if the library's entry count ever moves, and `idx % 30` wrapping hides exactly that.
  - **Where a label is assigned by index, pin the dependency's own ORDER — a count check and a shape check are both blind to a reorder.** This is the same defect class as the two planet-id spaces above: positional identity carried across a library boundary. `drik.muhurthas` names its entries from the insertion order of `jhora.const.muhurthas_of_the_day` while deriving the time slots from the index, so discarding `entry[0]` and labelling slot *i* with `_MUHURTA_NAMES[i]` is correct only while that key order holds. Measured 2026-08-05: transposing **two adjacent keys** — the shape a real upstream change takes — served window 1 as "Ahi" where the library called it `mithra` and window 2 as "Mitra" where the library called it `aahi`, with `degraded: False`, every entry still matching the contracted 3-tuple, the count still 30, the windows still tiling the day contiguously, and **all 82 tests then covering this limb green** (`tests/test_muhurat_deep.py` + `tests/test_panchanga_fail_closed.py`). Comparing served labels to `_MUHURTA_NAMES` cannot catch it — that is the constant they were copied from, so the assertion is tautological with respect to ordering. The library's `(name, flag)` sequence is therefore pinned position by position (`tests/test_muhurat_deep.py`, `_MUHURTA_POSITIONAL_SIGNATURE`), together with the label each slot must serve under. **Pin the dependency's own names, not a derived signature.** The auspicious flags are the tempting choice because they carry no transliteration risk, but measured on this table they catch only **11 of the 29** adjacent transpositions (37.9%) and 189 of the 435 total (43.4%) — the flag column takes only **two** values across the 30 positions, so most neighbouring pairs share one, and a transposition of two **same-flag neighbours** is invisible to it — whereas the names, being dict keys, are unique and so move under **every** transposition (29/29 and 435/435). A flags-only pin catches the `aahi`/`mithra` swap above and stays green on `rudra`/`aahi`, which both carry flag 0 and mislabels two windows just as thoroughly. Every count in this paragraph is **computed** from the pinned table by `tests/test_muhurat_deep.py::TestSignatureColumnDiscrimination`, which asserts each one: cite what that test computes, and never re-count the table by hand into prose here. That last clause is itself a correction — this sentence used to gloss the mechanism as a hand-counted run of identical flags, the run length was wrong, and it had been copied into two further places before anyone re-*derived* it instead of re-*reading* it. The flag is kept as a *second*, spelling-independent signature, because it is the only column that moves when a key holds its position while its auspiciousness value changes. The cost of pinning names is a red test on a benign upstream respelling — which lands only inside a deliberate dependency bump this repo already requires to be handled deliberately, and which is the moment the label correspondence should be re-derived anyway. Production keeps discarding `entry[0]` rather than comparing it (`bphs_core/muhurat.py`, comment at the parse loop): comparing there would make a harmless respelling a 500 on every request, and the served path cannot tell a respelling from a reorder without the same pinned table.

## API contract stability

Endpoints are versioned under `/v1/*` (chart, strength, dashas, yogas, transits, special-points, profile, muhurat, muhurat.lagna-shuddhi, muhurat.family-lagna-shuddhi, compat — all POST; plus GET /source, GET /healthz). Response models live in `app/schemas.py` and are the wire contract with the caller.

- A backward-incompatible change to any request or response schema (removed/renamed field, changed type or units, tightened enum) requires a version bump (a new `/vN/` path) — never an in-place mutation of `/v1`. Additive optional fields are fine. Never break `/v1` in place; the caller pins to it.
- `/source` (authenticated) returns `{source_url, commit}`, where `commit` is the cache-invalidation key resolved by `_resolve_version()` in `app/main.py` (called once at import, cached as the module-level `_COMMIT`): `GIT_COMMIT` env (baked at image build, Dockerfile `ARG`/`ENV`) is authoritative; the source-content hash `src-<sha256[:16]>` is the dev fallback; the literal `unknown` is the non-cacheable sentinel. Never substitute a fabricated commit for `unknown` — the caller keys its result cache on this value, and a wrong key serves stale astronomy.

## HTTP service hardening

- Auth fails **closed**. `app/auth.py` refuses to start (the `raise RuntimeError` in its module-level `if _TOKEN_REQUIRED:` block, on the verdict of `_token_weakness_reason`) when `ENVIRONMENT` is outside `{development, local, test}` and `CALC_SERVICE_TOKEN` is missing, a known placeholder, or shorter than 16 characters. `ENVIRONMENT` defaults to `production` precisely so a missing value is fail-secure — that default lives in `environment()` in `app/deployment.py`, the single definition both fail-closed guards read; `app/auth.py` only caches its verdict at import as `_TOKEN_REQUIRED`. Rules: (1) never change that default to a permissive value; (2) never add a code path that serves an authenticated endpoint when the token is unset outside dev; (3) token comparison uses `hmac.compare_digest` — never `==` (timing attack surface) — in `require_token`; (4) the app secret travels in its own header, `X-Calc-Service-Token`; `Authorization` is reserved for the platform's OIDC identity token — never merge the two into one header (`require_token`'s `x_calc_service_token` Header parameter, and the rule stated in its docstring).
- `/healthz` is intentionally unauthenticated (liveness probe, no sensitive body — the `@app.get("/healthz")` route in `app/main.py` deliberately carries no `require_token` dependency) — keep its body limited to a status string plus an `ephe_loaded` boolean; never add sensitive data to it.
- Validate every endpoint at the schema boundary: latitude `ge=-90, le=90`, longitude `ge=-180, le=180`, timezone `ge=-12, le=14`, and every float field carries `allow_inf_nan=False`. Hard rule on the NaN subtlety: `ge`/`le` alone do **not** reject NaN (IEEE-754 comparisons with NaN are always false), so a NaN value passes range checks and flows into `swe.houses()` / `drik.Place()`, producing a finite-but-wrong chart. Every new float input field **must** set `allow_inf_nan=False` (see `app/schemas.py` and the contract in `tests/test_coord_bounds.py`). Also bound expensive-scan inputs — date-range caps (`MAX_*_DAYS`), `step_seconds >= 60`, family members `2..6` — so a single request cannot force an unbounded compute.
- The 422 handler must never regress into a 500: `_validation_exception_handler` in `app/main.py` sanitizes non-finite floats and exception objects before serializing, through its `_sanitize_for_json` helper. Keep validation rejections as well-formed 422s.
- Keep-alive / stale-connection handling is a two-sided contract. Server side: uvicorn runs with `--timeout-keep-alive 75` (Dockerfile CMD) so idle pooled connections aren't closed out from under a client mid-send (which otherwise surfaces as an `httpx.ReadError`) — keep this value at or above any upstream/load-balancer idle timeout. Client-side retry of the residual race is the caller's responsibility, not this repo's. If you change one side of this contract, reason about both.
- CORS `allow_origins` is driven by the `ALLOWED_ORIGINS` env var (read at import into `_ALLOWED_ORIGINS` in `app/main.py` and passed to `app.add_middleware(CORSMiddleware, allow_origins=…)`; a bare `*` is rejected there at import) and is empty by default — this is a server-to-server service. Do not introduce a wildcard `["*"]` origin.

## Async scanning design — the GIL trade-off

The service runs single-threaded under Python's GIL. A wide date-range electional scan (up to `MAX_LAGNA_SHUDDHI_DAYS` days) can occupy a request thread for its full duration, starving concurrent chart requests and risking the caller's connection/proxy timeout. The async submit/poll endpoint (`app/jobs.py`) solves this: it hands back a job id immediately and runs the scan on a small background thread pool, decoupled from the submitting request's lifecycle.

**What it solves:** the connection timeout problem for long-running scans. The HTTP call that submits a scan returns right away; the caller polls for results separately.

**What it does NOT solve:** GIL contention. The background thread pool and the sync `/v1/*` handlers share the single process's GIL. CPU-bound scans and interactive chart requests still contend, degrading latency of concurrent sync handlers while a scan runs. The design's own module docstring in `app/jobs.py` already acknowledges this. The thread pool is deliberately kept small (`max_workers=4`) to bound the contention, and the design ensures submissions and polls (which only touch a lock-protected dict) remain O(1) and never wait on scan compute.

**Why the trade-off is accepted:** (1) it solves a real, reported problem (caller connection timeouts); (2) residual latency degradation is bounded by `max_workers=4` and occurs only during a scan; (3) the caller has a durable synchronous path (`/v1/muhurat`, `/v1/muhurat.lagna-shuddhi`) as the canonical route — the async variant is strictly additive; (4) job state is process-local and does not survive a restart, acceptable because the sync path remains intact; (5) no evidence of a breached latency SLO today.

**If the decision reverses:** should a latency SLO be breached or the caller profile change to many concurrent scans, isolate scan CPU in a subprocess or `multiprocessing.Pool` to eliminate GIL contention. This would require separate infrastructure (subprocess management, IPC, cleanup on restart) — acceptable at that point, but not now.

## Supply-chain & image hygiene

- The shipped Docker image installs from the committed, frozen lockfile: `Dockerfile` copies `pyproject.toml`/`uv.lock` into the build context and runs `uv sync --frozen` (once for third-party deps, once for the project itself), so the deployed dependency set is provably the tested one — there is no floating `pip install -e .` step left. Keep it this way; never reintroduce an unpinned resolve at build time.
- **Every external image is a digest-pinned `FROM`, never a `COPY --from=<registry image>` — and the two halves of that rule are independent.** Both Dockerfiles used to install the build tool with `COPY --from=ghcr.io/astral-sh/uv:latest /uv /uvx /bin/`, defended by a comment arguing a floating tag was fine for an installer. It was not, for two separate reasons, and fixing either one alone leaves the image floating. (1) `:latest` is re-resolved on **every** build, so two builds of the same commit can install different bytes with nothing recording which shipped — in an image whose every other input is pinned (`.python-version`, `uv.lock` under `uv sync --frozen`, the ephemeris files to sha256). - **No subprocess read may decode where the failure is invisible — and "add an `encoding=`" is NOT the rule.** `subprocess` in text mode decodes the child's output *inside subprocess*, on a reader thread on Windows, where a `UnicodeDecodeError` kills the thread instead of propagating and the caller is handed `stdout=None` with `returncode=0`. Measured on the locked interpreter (CPython 3.11.15, win32, cp1252) and reproduced on 3.12.10, against a child emitting bytes that are neither valid UTF-8 nor defined in cp1252: `text=True` → `stdout=None`; **`text=True, encoding="utf-8"` → `stdout=None`**; `errors="strict"` → `stdout=None`; `encoding=` alone (which implies text mode) → `stdout=None`; `universal_newlines=True` → `stdout=None`; `errors="replace"` → decodes, lossily; bytes mode then decoding in-process → a **catchable** `UnicodeDecodeError`. The second is load-bearing: **an explicit encoding does not remove the hazard, it only changes which codec dies on the reader thread**, so a guard that required an encoding and stopped there would have certified the broken shapes as fixed. What separates safe from unsafe is neither the codec nor the identity of the calling helper, but whether the decode *can raise where nobody is listening*. Two shapes are admitted: **(A) bytes mode**, where the caller decodes and the failure lands in its own frame — the shape for anything that SCANS content, because a scanner must refuse an unreadable input rather than scan a lossy rendering of it; and **(B) an explicit `encoding=` that resolves through `codecs.lookup` to canonical `utf-8`, paired with a non-raising `errors=`**, where the reader thread cannot die. **The codec restriction in (B) is not decoration**: shape (B)'s whole justification is that ASCII survives a lossy decode, and that is codec-specific — measured, one stray lead byte before an ASCII marker under `errors="replace"` leaves the marker intact under utf-8 but **destroys it under `cp932`, `cp936` and `utf-16`**, whose double-byte forms consume the following character. Single-byte codecs preserve ASCII too, but admitting them would reintroduce exactly the locale-flavoured decoding this rule exists to remove. **Refused** — the full list is registered in the guard as `_REFUSAL_GROUNDS` and this prose is checked against it, so it cannot fall behind the code: text mode with no explicit `encoding=` (the decode uses the **locale codepage**, so the verdict depends on the machine); an `encoding=` that `codecs.lookup` does not know, or that is not canonical utf-8 (see `cp932` above); a raising `errors=` policy, including the default `strict`; a **non-literal** value in any text-mode keyword, since text mode is decided by TRUTHINESS (`encoding or errors or text or universal_newlines`) and an unreadable value may well select it — **though only where nothing else settles the question, and the list over-claims without that qualifier**: a *definitely* truthy keyword answers it, so measured, `text=<expr>` beside a literal `encoding="utf-8", errors="replace"` classifies **lossy**, not refused (a bare `text=<expr>` is refused, and a non-literal `encoding=`/`errors=` always is, since those two are read directly rather than for their truth value); `subprocess.getoutput`/`getstatusoutput` and **`os.popen`** in any form, which decode with the locale and accept no encoding parameter at all; a `**kwargs` splat, a `*args` splat, or **more than one positional argument** — because `universal_newlines` is `Popen`'s 12th **positional** parameter and `run`/`check_output`/`call`/`check_call` forward `*popenargs` into it, so text mode can be selected with no keyword at all (measured: `run(cmd, -1, None, None, PIPE, PIPE, None, True, False, None, None, True)` returns a `str`, and a guard reading only keywords called that **safe**). Every one of those is the same principle: a guard that cannot prove its property fails closed. Shape (B) is crash-free but **lossy**, a semantic risk the guard cannot adjudicate, so every shape-(B) site is enumerated in `_LOSSY_DECODE_REGISTER` with the reason lossiness cannot change *that* site's verdict; the register is keyed by `(path, enclosing function)` resolved by AST and is **self-expiring** — an entry that no longer resolves to a lossy site fails as stale, so a justification cannot outlive the code it was written for. It vets the lossy *choice*, not helper identity: measured, `errors="strict"` inside a carefully written helper dies exactly as it does anywhere else. Contract: `ci/tests/test_subprocess_decoding.py`, which parses the AST (so a comment or string literal can neither satisfy nor defeat it), resolves the ordinary aliasing forms (`import subprocess as x`, `from subprocess import run as y`, `from subprocess import *`, `sp = subprocess`) while **enumerating the forms it cannot reach in its own KNOWN BOUNDS** rather than claiming to catch them, cross-checks its text-mode rule against the **real engine**, and floors its inventory per form. Extend it, never weaken it.
- **A guard that enumerates the working tree must ask git for it in a form that cannot be re-encoded.** `ci/check_pytest_collection.py` used `git ls-files --cached --others --exclude-standard` without `-z`. Measured against a fixture repo holding a `pytest.ini` carrying `addopts = --collect-only` under a directory whose name is non-ASCII: the enumeration returned `'"caf/303/251/305/241/pytest.ini"'` and the checker reported **CLEAN**. That is the exact fail-open the checker exists to close, hidden behind a path component. `-z` disables quoting entirely and NUL-separates the records, so a path arrives verbatim whatever bytes it holds and whatever `core.quotePath` says — the shape `ci/tests/test_dockerfile_image_pins.py::tracked_dockerfiles` already used. The separator rewrite is **removed**, not kept: git emits `/` on every platform, so it had nothing left to do but corrupt a literal backslash in a POSIX filename, and records are no longer stripped either because with `-z` they are exact and a leading or trailing space is a legal filename character. An undecodable listing answers `None` — "git cannot answer" — which is not a silent pass: the caller falls back to `_walked_paths` and the tree is still scanned.
